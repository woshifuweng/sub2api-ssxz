# 使用记录密度与管理页顶部比例修复设计

## 目标

在不删除任何使用记录信息、不恢复 Sub2 原始视觉的前提下，降低客户“用量明细”表格的横向拥挤感；同时统一管理后台顶部标题、版本标识、描述文字和分隔线的垂直比例与基线。

## 已确认约束

- 使用记录中的 API 密钥、模型、推理强度、接口、IP/地区、分组、类型、计费方式、Token、费用、耗时、时间和定位码都必须保留。
- 关键信息应直接可见，不能再次只放进行内展开详情。
- 保留 SSXZ 黑白灰视觉；只复用 Sub2 已有数据与展示能力，不恢复 Sub2 原始蓝色 UI。
- 允许表格行高略增，以换取更少的列和更清楚的信息层级。
- 本轮不改计费、日志、筛选或导出数据口径。

## 方案比较

### 方案 A：继续压缩 13 列

减小字号、间距和列宽。改动最小，但会进一步降低可读性，长分组、定位码和 Token 明细仍容易拥挤，不采用。

### 方案 B：恢复 5 列并将其余字段放入展开详情

首屏最清爽，但用户必须逐条展开才能看分组、接口、IP 和定位码；此前已被明确判定为信息阉割，不采用。

### 方案 C：8 个组合列（采用）

把语义相关字段放在同一单元格上下两层：

1. API 密钥
2. 模型 / 推理强度
3. 接口 / IP 与地区
4. 分组 / 请求类型 / 计费方式
5. Token
6. 费用
7. 首字耗时 / 总耗时
8. 时间 / 定位码

所有字段仍在首屏表格中直接可见，列数从 13 降为 8；通过略增行高、主次字号和标签层级提升扫读效率。宽屏优先完整展示，窄屏仍允许容器内横向滚动，不能让整页产生横向溢出。

## 页面与组件设计

### 客户使用记录页

- `AppUsageView` 只为客户页面启用“组合列”模式，不改变管理端使用记录默认列结构。
- `UsageTable` 复用现有模型、IP 地区、分组、Token、费用、耗时和定位码渲染逻辑；新增组合展示入口，避免复制计费或格式化逻辑。
- 单元格采用两层信息：第一层为主要识别值，第二层为辅助信息；徽章保持克制，不让三枚标签横向争抢空间。
- 长 API Key 名、分组名和定位码使用省略号与完整 `title`；定位码保留复制能力。
- 移动端继续使用卡片布局，组合字段按相同语义分组，不减少信息。

### 管理后台顶部

- `AppHeader` 的标题块、版本标识统一在一个垂直居中容器中，版本标识与标题基线对齐，不再靠零散的上外边距校正。
- 顶部栏固定使用同一高度变量；左右内容均以该高度垂直居中。
- 标题、描述行高设为确定值，避免字体渲染差异导致顶部比例漂移。
- 顶部栏底部分隔线与侧栏头部底线使用同一颜色和同一物理像素位置。
- 仅修全局管理页顶部，不改变客户工作台页面头部或管理页面主体数据。

## 数据流与错误处理

- 请求、筛选、分页、排序、导出和 IP 地区获取流程保持不变。
- 组合列只消费现有 `UsageLog` 数据，不新增接口、不改数据库。
- 缺失字段继续显示 `-`；IP 地区查询失败沿用现有重试入口；复制失败沿用现有提示。
- 管理页顶部只涉及布局样式，无新网络请求和状态。

## 验收标准

- 桌面 1920、1440、1280、1024 宽度下，表格内部可读，页面本身无横向溢出；相较 13 列版本横滑距离显著减少。
- API 密钥、模型、推理强度、接口、IP/地区、分组、类型、计费方式、Token、费用、首字耗时、总耗时、时间和定位码均可直接看到。
- 长分组、长 Key 名、长定位码不覆盖相邻列；定位码仍可复制。
- 390px 手机下无页面横向溢出，卡片信息完整，按钮可点。
- 管理后台桌面端顶部标题、版本、描述和分隔线对齐；侧栏头部与主区域底线同高。
- 深色、浅色主题均无颜色回退；浏览器控制台无新增错误。
- 相关组件测试、类型检查、前端构建和完整前端测试通过。

## 发布与回滚

- 先生成候选版本并在测试环境验收，再按现有备份流程发布正式环境。
- 正式发布前保留当前二进制、配置和数据库备份；若页面回归或关键门禁失败，恢复上一正式二进制。
- 发布后用管理员和普通用户分别验收管理页顶部、使用记录筛选、横滑、定位码复制和移动端布局。
