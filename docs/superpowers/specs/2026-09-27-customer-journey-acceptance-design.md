# 客户路径完整验收与修复设计

## 目标

让客户在 PC 和移动端都能完成核心任务，并且每个结论都有可复现证据：登录、注册、验证码、创建 API Key、选择模型、发起请求、余额提醒、图片工作台、账户头像编辑、兑换/订阅、使用记录、渠道状态和文档登录状态。

四个新增模型 GPT-6 Sol、GPT-6 Luna、Claude Opus 5.5、Grok 4.7 只有在隔离测试账户完成真实最小请求并记录有效模型、返回结果、计费、延迟和上游渠道后，才可以标记为“已验证可用”；仅有代码白名单、页面名称或官方发布说明不能替代实测。

## 根因判断

之前的检查偏重页面能否打开、接口是否返回 200 和后台桌面端是否显示，缺少客户视角的“任务完成”检查。项目同时存在多套模型目录/头像路径/登录状态入口，且没有一份把来源、运行配置、真实返回和 PC/移动端操作串起来的回归矩阵，因此页面看起来正常仍可能在点击、拖动、刷新、深链、过期登录或真实请求时失败。

## 验收边界

### P0：阻塞客户使用

- 四个目标模型的真实最小请求与响应证据。
- API Key 创建后能在列表中出现并能被实际请求使用。
- 模型卡片选中状态、提交参数和实际计费模型一致。
- PC/移动端登录、注册、验证码、过期会话和深链恢复。
- 余额预警阈值来源统一，显示金额与触发条件一致。
- Cloudflare/反向代理/后端慢请求时，不出现永久转圈；有明确超时、重试和错误提示。

### P1：核心功能不完整

- 头像选择、裁剪、拖动、缩放、保存和刷新后的持久化；鼠标和触摸手势均验证。
- 文档页登录状态与主站一致。
- 仪表盘、使用记录、渠道状态和渠道定价的入口/数据含义清晰且不重复误导。
- 移动端导航、模型入口、外部商店库存/补货状态、兑换流程。

### P2：体验与防回归

- 空数据、慢请求、网络失败、权限不足、重复点击和刷新恢复。
- 浏览器控制台错误、未处理 Promise、关键请求耗时和大页面性能预算。
- 发布来源、运行配置、数据库/数据目录和回滚证据。

## 实施原则

1. 先复现并登记，再修复；每个问题包含角色、路由、设备、前置条件、实际结果、期望结果和验证证据。
2. 统一来源，不在前端继续维护与后台/运行配置脱节的模型真值；无法证明线上可用时显示“未验证”，不伪装成可用。
3. 真实模型探针只能使用隔离 QA 账号和最小成本请求；没有隔离额度或授权时只做配置/链路检查，不擅自消耗客户余额。
4. 修复必须同时覆盖组件测试、接口契约和 PC/移动端浏览器验收。
5. 正式发布前必须通过来源校验、运行链接校验、页面 HTML 校验、关键路径点击和回滚检查。

## 交付物

- 机器可读的客户问题/验收矩阵。
- 模型可用性探针结果和请求证据（脱敏）。
- 组件/API/浏览器回归测试。
- 修复后的版本与发布前预检记录。
- 最终验收报告：已完成、未完成、阻塞项、线上是否更新、客户如何复测。
